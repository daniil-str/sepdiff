# SEPDiff — план разработки

«git log» для Stanford Encyclopedia of Philosophy: история правок любой статьи,
собранная из квартальных архивных изданий. Работают CLI, веб на htmx,
отслеживание статей с Atom-лентой и экспорт истории в настоящий git-репозиторий.
Этапы 0–5 закрыты — что и когда сделано, с числами, в [журнале](docs/journal.md).

Этот файл — рабочий, а не исторический. В нём два главных раздела:
**как мы ведём работу** (раздел 2 — ревью перед GitHub) и
**что делать дальше** (раздел 6). Знание о предметной области —
[docs/domain.md](docs/domain.md), как пользоваться — [README.md](README.md),
короткая выжимка правил для агента — [CLAUDE.md](CLAUDE.md).

## 1. Где мы сейчас

Работает:

- `fetch` — сканирование статьи по фазам: грубый проход через каждое 8-е
  издание, бинарный поиск точек правки, потом добор остального. Читаемая
  история появляется через пару минут, а не через двенадцать;
- `log` / `diff` / `show` — история, пословный diff, текст версии;
- `live` — текущая версия на сайте: правка попадает в архив только со
  следующим кварталом, а на сайте видна сразу;
- `watch`, `feed`, `/feed.atom` — отслеживаемые статьи, обход раз в час;
- `export-git` — история статьи как репозиторий: `git log`, `git blame`;
- `serve` — веб: поиск, история, diff, сканирование в фоне с прогрессом;
- 116 изданий (fall1997 — sum2026), три эпохи вёрстки, классификация правок
  сверена с эталоном самого SEP.

Данные: `data/` — 18 МБ, 450 снимков (7 статей), оглавление на 1856 статей,
база схемы v5. Проверка: `uv run pytest` — **504 passed, 5 xfailed**
(12.09.2026).

Репозиторий на GitHub, публичный, CI на каждый PR (раздел 2.5).

## 2. Как мы работаем

**Правило: в `main` ничего не попадает без ревью и мёржа владельцем репозитория
на GitHub.** Агент никогда не пушит в `main` и не мёржит свою ветку сам —
даже когда CI зелёный и тесты проходят: смёржить Pull Request — решение
владельца, а не техническая формальность.

Ветку и PR к ней агент открывает без отдельного разрешения на каждый раз —
открытие PR и есть просьба о ревью, а не действие в обход него. Explicit-permission
из общих правил безопасности касается push в `main` и мёржа — не push
ветки `task/…` и не `gh pr create`, это рутинный шаг цикла (2.1).

### 2.1 Цикл одной задачи

1. **Взять одну задачу** — из раздела 6 или ту, что назвал владелец. Пока её
   PR не смёржен или не отклонён, вторую не начинать.
2. **До кода сказать план в 3–5 строк**: что меняем, в каких файлах, чем
   проверим. Если по ходу выяснилось, что задача вдвое больше — остановиться и
   сказать, а не растить коммит молча.
3. `git switch -c task/<короткое-имя>` от свежего `main`.
4. Код и тесты вместе. Тест, который до правки падал бы, обязателен везде,
   кроме чистого переноса кода.
5. Проверить (раздел 5). Если правка касается сети или разбора — прогнать
   вживую через прокси и запомнить числа.
6. **Прочитать свой diff целиком** (`git diff main...HEAD`): убрать отладку,
   случайные переформатирования и файлы, попавшие «за компанию». Пройти
   чек-лист раздела 3.
7. Закоммитить, запушить ветку и **открыть PR** (2.2) — описание PR и есть
   отчёт на ревью. После этого — остановиться; не начинать следующую задачу
   в ожидании ответа.
8. Владелец мёржит (или просит доработать) на GitHub сам. После мёржа —
   `git fetch --prune && git switch main && git pull --ff-only`, локальную
   ветку задачи удалить (`git branch -d task/<имя>`).

### 2.2 Что писать в отчёте на ревью

Пять пунктов, не пересказ diff:

- **Зачем** — одна-две фразы: какую задачу это закрывает.
- **Что изменилось** — по строке на файл, почему он тронут.
- **Как проверено** — команды и результат: сколько тестов, что прогнали
  вживую, какие числа получились.
- **Что не проверено и чем рискуем** — честно. «Не проверял на вёрстке
  1997 года» — нормальный пункт отчёта; «всё работает» — не пункт.
- **Куда смотреть в первую очередь** — одно-три места, где ошибиться было
  легче всего.

Сам diff показывать в панели изменений приложения, а не вываливать в чат.

### 2.3 Правки после ревью

- Замечания правим в той же ветке, новыми коммитами: ветка уже на GitHub и,
  возможно, открыт PR — переписывать историю (`--amend`, `rebase`) значит
  заставить владельца заново сверять то, что он уже посмотрел.
- В ответе сказать, что сделано, а что сознательно не сделано и почему.
  «Оставь как есть» — это решение владельца, а не повод для спора.

### 2.4 Размер коммита

Ориентир — diff, который человек прочитает за 10–15 минут: **до ~400 строк**,
не считая тестов и сгенерированного. Больше — делить:

- механическое (перенос, переименование, автоформатирование) — отдельным
  коммитом от смыслового, иначе ревью тонет в шуме;
- миграция схемы и работающая на ней логика могут ехать вместе, но тогда
  коммит только про это.

### 2.5 GitHub

Репозиторий: [github.com/daniil-str/sepdiff](https://github.com/daniil-str/sepdiff),
публичный. `data/` и любые тексты SEP там не появятся — их нет в git вообще
(domain.md, раздел 5).

На каждый push и Pull Request прогоняется CI (`.github/workflows/ci.yml`):
`uv run pytest` и `uv run ruff check`. Зелёный CI — необходимое условие,
не достаточное: он не гоняет `test_real_snapshots.py` (в репозитории нет
`data/`), так что регрессию на реальных данных по-прежнему проверяет и
называет числами агент — в отчёте на ревью (2.2).

Мёрдж, закрытие и повторное открытие PR — только владелец, на GitHub.
Агент никогда не пушит в `main` и не жмёт «Merge» сам, даже когда CI
зелёный. После мёржа: `git fetch --prune && git switch main && git pull
--ff-only`, ветку задачи удалить локально и на GitHub (или дать это сделать
кнопке «Delete branch» в PR — тоже нормально).

## 3. Что должно быть в коммите

- [ ] одна тема; механические правки отделены от смысловых;
- [ ] `uv run pytest` зелёный, число тестов не уменьшилось (уменьшилось —
      объяснить в отчёте);
- [ ] новое поведение покрыто тестом; тесты в сеть не ходят;
- [ ] тронут разбор HTML → поднят `EXTRACT_VERSION`; тронута схема → поднят
      `SCHEMA_VERSION` и добавлена запись в `MIGRATIONS`;
- [ ] `git status` после коммита чист: `data/`, `.venv`, кеши не в индексе;
- [ ] изменилось пользовательское поведение → поправлен README; принято
      решение, подтверждённое числами → абзац в `docs/journal.md`;
- [ ] сообщение: тема по-английски, повелительное наклонение, ≤ 72 символов;
      тело — зачем, а не что; трейлер `Co-Authored-By:` ровно в той форме,
      которую даёт харнесс.

## 4. Инварианты

Это не стиль, это то, что ломает данные или отношения с чужим сервером.

1. **Архивные издания иммутабельны.** Скачанный снимок не перекачивается
   никогда — ни «на всякий случай», ни при отладке.
2. **Пять секунд между запросами** на весь процесс, в том числе между
   запусками (отметка в `data/.last_request`). `CRAWL_DELAY` не уменьшать,
   запросы не параллелить.
3. **Закрытые robots.txt пути** (`/cgi-bin/`, `/diffs/`, `/search/`, `/rss/`,
   `/perl/`) отклоняет сам фетчер — это не забота вызывающего кода.
4. **`data/` священна.** 450 снимков — это почти час честного краулинга и
   единственная копия. Не удалять, не чистить, не пересоздавать базу «чтобы
   проверить миграцию»: для этого есть временный каталог через `$SEPDIFF_DATA`.
5. **Тексты SEP не публикуются.** `data/` вне git; экспорт несёт
   предупреждение о копирайте.
6. **Ядро не знает про веб** (см. раздел 1).
7. **Классификация меняется только против эталона.** Сейчас находятся 120 из
   125 правок, записанных самим SEP (domain.md, раздел 8). Стало меньше — это
   регрессия, а не «обновлённый эталон».
8. **Разбор → `EXTRACT_VERSION`, схема → `SCHEMA_VERSION` + миграция.** Старые
   базы обязаны открываться после обновления кода.
9. **Тесты не ходят в сеть.** Никогда, ни под каким флагом.
10. **Интерфейс по-русски**, ошибка пользователю — фраза для человека, а не
    трейсбек.
11. **Сеть с этой машины — только через прокси** `HTTPS_PROXY=http://127.0.0.1:2080`
    и только для своего процесса; системные настройки не трогаем.

## 5. Как проверять

```bash
uv run pytest
```

**504 passed, 5 xfailed** (12.09.2026). Тесты работают на фейковом сайте
(`tests/fakes.py`, `tests/pages.py`).

`tests/test_real_snapshots.py` — регрессия на настоящих снимках из `data/`:
440 пар соседних изданий против эталона archinfo. Если `data/` пуст, тест
молча пропускается; значит, проверка была неполной — так и сказать в отчёте.

Живая проверка, когда правка касается загрузки или разбора: одна статья,
`--quick`, числа — в отчёт.

```bash
HTTPS_PROXY=http://127.0.0.1:2080 uv run sepdiff fetch russell-paradox --quick
```

Веб — через панель предпросмотра (`.claude/launch.json`, порт 8765), а не
`uvicorn` из терминала: посмотреть страницу, консоль браузера и приложить
скриншот.

CI на GitHub (2.5) прогоняет то же самое автоматически на каждый PR —
`uv run pytest` и `uv run ruff check`, но не `test_real_snapshots.py`
(нет `data/`) и не живую проверку через прокси. Эти две — по-прежнему
на агенте, вручную, с числами в отчёте.

## 6. Очередь задач

Порядок сверху вниз, если владелец не сказал иначе. У каждой: зачем, что
сделать, чем проверяется, размер и нужна ли сеть. Нумерация не переиспользуется:
T1 и T8 закрыты (ниже), следующая новая задача — T9.

**Закрыто:**

- **T1. Одна команда проверки** — `ruff`, конфиг. [PR #2](https://github.com/daniil-str/sepdiff/pull/2).
  CI, который её запускает на каждый PR, — отдельно, раздел 2.5.
- **T8. Публикация на GitHub** — репозиторий, LICENSE, `.gitignore`. [PR #3](https://github.com/daniil-str/sepdiff/pull/3).

### T2. Дополнительные документы статьи (L, нужна сеть, 2–3 коммита)

**Зачем.** Два из четырёх пропусков против эталона — правки внутри
`notes.html` и подобных. Экстрактор уже собирает их список (`Doc.supplements`),
но сами документы не скачиваются.

**Что.** (1) Хранение: снимок дополнительного документа — либо колонка
`document` в `snapshots`, либо своя таблица; решение записать в журнал вместе
с миграцией схемы v6. (2) Скачивание по флагу `fetch --supplements`, по
умолчанию выключено: это плюс один запрос на документ **на каждое издание**,
у больших статей — часы. (3) Классификация: отдельный хеш документов участвует
в `classify` наравне со `struct_sha`; вид правки по-прежнему решает дата на
основной странице.

**Приёмка.** Синтетическая статья с supplement в `tests/pages.py`: правка
только в нём попадает в историю. На реальных данных закрываются два известных
пропуска. README и журнал.

**Осторожно.** Не заставить уже скачанные статьи перекачиваться заново
(инвариант 1).

### T3. Diff «рядом» (M, без сети)

**Зачем.** Длинные правки построчно читать тяжело; переключатель был в
исходном плане и не сделан.

**Что.** На странице diff переключатель «построчно / рядом». Состояние — в
query-параметре (`?view=side`), чтобы ссылка воспроизводилась; панель
подменяет htmx; на узком экране колонки схлопываются в одну средствами CSS,
без JS.

**Приёмка.** Тест маршрута на оба значения; при ширине 375 px страница не
даёт горизонтального скролла; скриншот в отчёте.

### T4. Blame в вебе (M, без сети)

**Зачем.** Главный вопрос читателя — «в каком издании появился этот абзац».
В `export-git` это уже работает через `git blame`, в вебе нет.

**Что.** `/e/{slug}/blame`: текст последней версии, у каждого абзаца — издание,
в котором он появился. Считается по цепочке ревизий, сопоставление блоков уже
есть в `diffing._align`. Померить на статье со 116 изданиями; дольше секунды —
кешировать.

**Приёмка.** Тест на фейковой истории; на настоящем `kant` результат совпадает
с `git blame` экспорта.

### T5. Переименования статей (M, для проверки нужна сеть)

**Зачем.** SEP не делает редиректов: смена слага сейчас выглядит как `removed`
плюс новая статья без истории.

**Что.** Ловить 301/302 у живой версии, таблица `aliases` (миграция), сшивать
историю; в истории — отметка «до fall2019 статья называлась иначе».

**Приёмка.** Фейковый сайт с редиректом. Настоящий пример искать так: в
оглавлениях двух соседних изданий найти пропавший slug и появившийся с тем же
заголовком.

### T6. Незнакомые картинки-символы (S, без сети)

**Зачем.** Незнакомая `[img:имя]` — тихий источник ложных правок в статьях по
логике: когда SEP заменит картинку на Unicode, мы покажем правку, которой нет.

**Что.** Собирать при разборе имена, которых нет в `SYMBOL_IMAGES`; отчёт по
всем скачанным снимкам (команда или вывод в конце `fetch`); частые — в словарь.

**Приёмка.** Тест на синтетической странице; прогон по `data/` с перечнем
находок в отчёте.

### T7. Обход по расписанию без сервера (S, без сети)

**Зачем.** `watch --check` есть, но человек не знает, как повесить его на
расписание.

**Что.** Раздел в README: планировщик Windows (`schtasks`) и cron, с прокси и
`SEPDIFF_DATA`. Проверить, что вывод годится для лог-файла: без ANSI-цветов,
когда вывод не в терминал.

**Приёмка.** Команда из README ставится и отрабатывает.

### Дальше, по вкусу

Экспорт в текст и PDF (остаток этапа 4), diff по разделам («что стало с §3 за
десять лет»), детекция перемещённых абзацев, публичная версия только с
метаданными (без текстов).

## 7. Чего мы не делаем

- не публикуем тексты SEP и не делаем зеркало;
- не ускоряем краулер и не обходим robots.txt — ни параллелью, ни другим
  прокси, ни через Wayback;
- не ходим автоматически в `archinfo.cgi`: эталон снимается руками;
- не добавляем зависимости без нужды — каждая это строка в `uv.lock` и лишний
  повод сломать `uv sync`;
- не заводим сборку фронтенда, Node, ORM, Celery и Redis;
- не рефакторим «заодно»: рефакторинг — отдельная задача с отдельным ревью;
- не запускаем длинные сканирования без спроса: одна статья — до двенадцати
  минут и сотня запросов к чужому серверу.
